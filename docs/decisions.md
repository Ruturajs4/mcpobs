## Finding D13 — RESOLVED 2026-08-15 by D17

> **Status: resolved.** The finding below stands as written — the taxonomy is
> genuinely not reachable *from span attributes*. What changed is that it does
> not have to be: the distinguishing text is SDK-generated boilerplate present
> in the result, and a middleware can classify it in the customer's process and
> annotate the span the SDK already opened.
>
> Verified end to end: `server_exception`, `tool_error`, `unknown_tool` and
> `invalid_arguments` are now distinct on real telemetry, with zero tool content
> stored (assertions A3b, B1–B3). The V2 §25 launch gate is met.

## Original finding — the failure taxonomy is not reachable from span attributes

**What we tested.** Four deliberately distinct failure modes:

| Scenario | Intent |
| --- | --- |
| `soft_fail` | tool returns `CallToolResult(isError=True)` |
| `explode` | handler raises `RuntimeError` |
| `no_such_tool` | call to an unregistered tool |
| `echo_fast({"message": {...}})` | schema-violating argument |

**What we got.** All four produce an identical span: `status=ERROR`,
`error.type="tool_error"`, no `rpc.response.status_code`, no exception event.

**Cause.** `MCPServer`'s tool handler catches everything and converts it to
`CallToolResult(isError=True)` *before* `OpenTelemetryMiddleware` observes the
result. The middleware's `except MCPError` and `except Exception` branches
(`mcp/server/_otel.py:45-60`) are therefore unreachable for anything routed
through `tools/call`.

**Consequences.**

1. Day-1 doc §9.5 lists five categories; two are reachable.
2. V2 §25's launch checklist item *"MCP isError and thrown exception are
   distinguishable"* is **not achievable from span attributes** with the stock SDK.
3. V2 §6.3 sells an MCP failure taxonomy as a core differentiator. Today that
   taxonomy has one failure bucket.

**Options for Day 2** (none chosen yet):

- Inspect `CallToolResult` content text — distinguishes the cases, but content is
  a payload feature (opt-in, redaction-gated per V2 §15), so the taxonomy would
  inherit payload-capture constraints.
- Contribute an upstream SDK change so the middleware sees the original failure.
- Ship a documented single failure bucket for v1 and revisit.

This is the most important thing Day 1 found. It belongs on the Day-2 agenda,
not in a backlog.

| D26 | 2026-08-15 | "Is recent data healthy?" must be asked in **event time**, never ingest time. | Replay deliberately decouples the two clocks: it re-ingests old spans *now*, so `ingested_at` cannot isolate a current run. Found when a helper-coverage assertion failed against replayed history. |

| D27 | 2026-08-15 | Record the platform's clock resolution in `docs/observed_attributes.md`, and assert duration measurability (B8) rather than trusting fast-tool latency. | 52% of local `tools/call` spans had `duration_ns = 0`. OTel timestamps spans with `time.time_ns()`, whose smallest tick on this Windows host is **0.75 ms** — so anything faster records as zero and p50 for `echo_fast` reads 0 ms. Linux is nanosecond-grade, so production is very likely unaffected; a customer on Windows would not be. Reported as WARN, not FAIL: an environment property, not a defect. |

| D28 | 2026-08-15 | **Stitch MRTR round-trips, and report BOTH numbers.** Correlate via a hash of `requestState`; never store the blob. | Measured (`scripts/mrtr_experiment.py`): one logical tool call produces **2 `tools/call` spans that do NOT share a trace_id** — the client's retry starts a new trace. The only link is `requestState`, which the server emits on the asking round and the client echoes back on the answering round. Server-observed time was **3.00 ms vs 405 ms** of real wall clock — a **135×** understatement — so reporting either number alone is wrong: "server time" is the SLO number, "logical wall clock" is the UX number. |
| D29 | 2026-08-15 | Latency eligibility is a **stored column**, not a query-time filter. | A `subscriptions/listen` duration is a stream lifetime and an MRTR interim round excludes client think-time. | D30 | 2026-08-15 | `ctx.elicit()` is NOT the MRTR path. | D31 | 2026-08-15 | A client without elicitation capability gets `-32021 MissingRequiredClientCapability`, not an interim result — confirming D19 on real telemetry. | This is a *protocol* failure, legitimately span-sourced: the `MCPError` propagates rather than being converted, so the helper never sees a result. | D32 | 2026-08-15 | The pipeline emits **metrics, not traces**, about itself (V2 §19). | Tracing the normalizer means emitting spans about the act of storing spans: volume scales 1:1 with customer traffic and our own telemetry becomes our largest tenant. | D33 | 2026-08-15 | Self-telemetry uses a **separate Collector pipeline** that never touches Kafka or a customer tenant. | The outage that breaks ingestion must not also blind us to it. Metrics survive a Kafka or ClickHouse failure precisely because they do not depend on either. |
| D34 | 2026-08-15 | Insert failures are counted **before** the exception is re-raised. | An insert failure that is invisible is the one that becomes silent data loss. |

| D35 | 2026-08-15 | **`opentelemetry-instrumentation-dbapi` wraps `Cursor.execute`, NOT `Connection.execute`.** The idiomatic one-liner produces no span at all. | Verified, not assumed: `connection.execute(...)` emitted zero spans; the same query through an explicit cursor emitted them correctly. | D36 | 2026-08-15 | Promote `db.operation` / `db.collection`, never `db.statement`. | Statement text can contain inlined literals — customer identifiers, emails, anything a developer put in the SQL — so capturing it is payload capture under a different name (V2 §15). | D37 | 2026-08-15 | Derive `downstream_kind` at normalize time (`http` \| `db` \| `llm` \| `messaging` \| `internal`). | The waterfall should not re-derive it per query, and "unexplained server time" becomes a value you can filter on rather than an absence you must infer. |

| D38 | 2026-08-15 | **`insert_deduplication_token` works — but only when batch boundaries are identical.** ADR-006 covers crash recovery, not operator replay. | Proven, finally, by running ReplicatedMergeTree locally. A crashed consumer re-reads the same offsets, forms the same batch, produces the same token, and the redelivery is discarded — which is the case ADR-006 was written for. An operator replay batches differently (the live consumer flushes on a 5s timer; a replay drains everything at once), so the token differs and rows are re-inserted. **That is correct**: a bug-fix replay must produce new rows at a higher `normalization_version`, and dedup would actively prevent the fix from landing. D24's version-resolved reads are the mechanism there, not a workaround. |
| D39 | 2026-08-15 | Every insert sets `deduplicate_blocks_in_dependent_materialized_views = 1`. | Without it deduplication is **half-applied**: ClickHouse discards the duplicate block in `spans_raw` but still propagates it to dependent materialized views. A replay left `spans_raw` correct while `trace_summaries` counted 160 spans against 120 actual. Aggregates silently disagreeing with the table they are built from is the worst failure mode available — nothing errors, and every dashboard is wrong. Caught by assertion B4. |
| D40 | 2026-08-15 | Run **ReplicatedMergeTree + embedded Keeper locally**, not just in production. | Three deferrals ("test it in staging") were hiding two real defects for two days. A local environment that cannot exercise the production engine does not de-risk anything; it postpones the discovery. Cost: one config file and a longer startup. |
| D41 | 2026-08-15 | Mount the Keeper config **file**, never the `config.d` directory. | Mounting the directory shadows the image's own `docker_related_config.xml`, which is what sets `listen_host`. The server then binds to 127.0.0.1 only, so every in-network client gets "connection refused" while `docker exec` keeps working — a confusing failure that looks like a network problem. |

| D42 | 2026-08-15 | `_number()` guards every float leaving the query API; `value or 0` is banned. | **NaN is truthy in Python**, so `quantile(...) or 0` passes NaN straight through and `json.dumps` then raises — a 500. ClickHouse returns NaN from `quantile()` over an empty set, which is exactly a brand-new tenant with no telemetry. **A new customer's first-ever page load was an error.** Found only because assertion C5 checks that an unknown tenant sees nothing; no amount of local data would have surfaced it. |
| D43 | 2026-08-15 | `/errors` filters in SQL, never after pagination. | Post-filtering a page means a window whose most recent traces all succeeded returns an EMPTY error list while errors sit just past the page boundary. An error view that looks healthy is the worst lie it can tell. |
| D44 | 2026-08-15 | Every span read goes through `LATEST_SPANS`; endpoints never write SQL. | Puts D24 (version resolution) and tenant scoping in exactly one place, so neither can be forgotten by an endpoint author. Guarded by tests that assert the SQL still contains `argMax`, `{tenant:String}` and `{project:String}`. |
| D45 | 2026-08-15 | A `DELETE FROM spans_raw` does **not** propagate to materialized-view targets. | MVs fire on INSERT only. Deleting from a source table silently desynchronises every aggregate built on it — learned by doing it and permanently skewing `trace_summaries` in dev. |

| D46 | 2026-08-15 | **Freshness uses a fixed 15-minute window, ignoring the user's selected range.** | It answers "is the pipeline healthy *now*", not "what was it historically". A 24h range swept in replayed spans — whose event time precedes ingest time by hours *by design* (D26) — and reported **19,820 s** of latency. It was measuring a replay, not the pipeline. Caught by looking at the UI, not by any test. |
| D47 | 2026-08-15 | Synthetic test data lives in its own tenant (`_verify`), never in `local`. | The idempotency probe was showing up in the console as a second "server". Test fixtures must be invisible to product queries — and a separate tenant exercises the scoping while it is at it. |
| D48 | 2026-08-15 | The console is served by the query API itself: one file, no build step, no framework. | A Phase-0 proof does not need a frontend toolchain, and adding one would make it the largest thing in the repo. One process, no CORS, no separate deploy. |

| D49 | 2026-08-15 | **Error text from failing tool results is captured by default** (`capture_error_detail=False` opts out). | 140 of 146 failing spans carried no message anywhere: the SDK's reachable branch calls `set_status(StatusCode.ERROR)` with no description (D13), so `status_message` is empty and "what went wrong" was unanswerable. Bounded to 512 chars, failing spans only, and written to its own `failure_detail` column so payload capture (DF-8) stays a separate opt-in and assertion B2 still passes. **A weaker privacy default than D17's absolutism** — an exception string can contain user data — so the README discloses it in the integration snippet itself, not an appendix. Revisit when a design partner has a view. |
| D50 | 2026-08-15 | The helper recovers `mcp.resource.uri` from `params["uri"]`. | `OpenTelemetryMiddleware` derives its target from `params["name"]`, which `tools/call` and `prompts/get` have and `resources/read` does not. So resource spans said "a read happened" and never what was read — neither span name nor any attribute carried it. This is structural addressing, the analogue of a tool name, not payload. |
| D51 | 2026-08-15 | A trace opens in a **right-hand drawer over the list**, not a new page. | Debugging is comparison — you bounce between traces — and navigating away loses the list you were working through. `Esc` closes; the URL still carries `?trace=&span=` so both stay linkable. |
| D52 | 2026-08-15 | **Every alias in a generated `argMax` projection is prefixed** (`s_<column>`). | Unprefixed aliases bit three times: `AS timestamp` made the `WHERE toDate(timestamp)` resolve to the aggregate, and `AS normalization_version` made the ranking column inside every other `argMax` resolve to an aggregate. Both surface as ILLEGAL_AGGREGATION with a confusing message. Rows are read positionally, so aliases are cosmetic and prefixing eliminates the class. |
| D53 | 2026-08-15 | Tools, prompts, resources and protocol methods share **one query path** (`capabilities(kind)`) and one view. | They are the same question asked of different `mcp_method` values. Four near-identical implementations would drift apart; one cannot. `protocol` deliberately matches everything not a capability invocation, so a newly added MCP method cannot vanish the way `tools/list` did. |
| D54 | 2026-08-15 | Self-time is computed server-side and shown as a solid segment inside a faded total bar. | `total − Σ children` needs the whole trace, so it belongs where the data is. It is the difference between "this tool is slow" and "this tool waits on something slow" — `fetch_status` is 7.8ms own work inside 10.4ms total, which duration alone cannot express. |

| D55 | 2026-08-15 | **Tool request/response capture, OFF by default** (`capture_payloads=True`), truncated to 2048 chars and pattern-redacted. | Clicking a span showed no request or response, which is the first thing anyone opens a span to see. Off by default — unlike error detail (D49) — because this is every argument and every result of *every* call, not just failures: a tool named `get_customer` returning a customer record is the normal case. V2 §15 specifies opt-in, redactable, size-limited, and this follows it. The demo server enables it so the capability is visible; a real server should choose deliberately. |
| D56 | 2026-08-15 | Redaction is documented as **incomplete**, not as a guarantee. | It catches field names (`password`, `token`, `api_key`, …) and value shapes (bearer, `sk-`, `ghp_`, AWS keys, JWTs). It will not catch a secret in a field called `note`. Saying so in the docstring and README is the difference between a safeguard and a false promise. |
| D57 | 2026-08-15 | Assertion B2 changed shape: from "no payload columns are populated" to "payload capture is off by default, and the taxonomy works without it". | The original was right while the feature did not exist, but it asserted *emptiness* rather than the property that matters. Kept as B2 + B2b so the guarantee — precise classification with zero payload stored — is still checked (140 such failures). |
| D58 | 2026-08-15 | Non-text content blocks (image, audio, resource) are summarised by type, never dumped. | A base64 image is megabytes of noise that tells an operator nothing and would dominate storage. |

| D59 | 2026-08-15 | **Promote `http_url` and `db_statement`, redacted at normalize time — reversing D36.** | D36 said "never promote `db.statement`" for privacy. But it was already stored **unredacted** inside `span_attributes` and rendered in the console's raw-attribute list, so not promoting it bought nothing: the value was in the row either way, just somewhere less obvious. That is privacy theatre. Promoting it *with redaction* — and redacting it in the raw map too — is strictly safer than the status quo as well as more useful. `http.url` had the same problem and worse: `?api_key=…` query strings were flowing in untouched. |
| D60 | 2026-08-15 | HTTP request/response **bodies are not captured**, and the console says so on the span rather than showing a blank. | Two reasons: the OTel HTTP instrumentation does not record bodies, and `mcpobs` wraps the MCP *server*, not the customer's outbound HTTP client. Capturing them would mean instrumenting a different thing. The span shows what genuinely exists — method, URL, status — and names the limitation, because an empty panel reads as a bug. |
| D61 | 2026-08-15 | Request/Response in the span panel **adapts to span kind**. | Rendering only the MCP shape is why downstream calls looked empty. An HTTP span's request *is* its URL; a DB span's request *is* its statement; an LLM span's is its model and token counts. All were already stored and none were surfaced. |
| D62 | 2026-08-15 | Redaction happens **before storage, never before display**. | A secret that reaches the table cannot be recalled: it is in backups, in the Kafka replay window, and in every downstream copy. Render-time redaction protects the screen and nothing else. |

| D63 | 2026-08-15 | **Payloads are captured as the full JSON-RPC message, not a fragment.** | The first version stored `params["arguments"]` and the first text block — `{"code": 200}` / `downstream returned 200`. That is not a protocol message, and this is an MCP observability product: the useful artefact is the wire message you can compare against the spec or paste into a bug report. |
| D64 | 2026-08-15 | Capturing `_meta` recovers **client identity**, which we had written off as unavailable. | The T3 report recorded that the SDK emits no client attribute on the span, so "which client called this tool" (V2 §6.1) looked impossible. It is in `_meta.io.modelcontextprotocol/clientInfo` on **every request**, along with `clientCapabilities` — the first thing to check on a capability error — and `traceparent`. All of it was being discarded. |
| D65 | 2026-08-15 | Response capture reads the whole `result`, not `content` blocks. | Looking for `content` meant `prompts/get` (returns `messages`) and `resources/read` (returns `contents`) captured **nothing at all**. It also drops `structuredContent`, the typed result, which was invisible. |
| D66 | 2026-08-15 | `requestState` is redacted inside captured payloads. | It carries recorded elicitation outcomes — the user's actual answers (D28). We hash it for MRTR correlation *precisely because* it must not be stored; capturing the whole params object would have let it ride along in plain text. Found by asking what the new capture now includes that the old one did not. |

| D67 | 2026-08-15 | **D60 revised by measurement: HTTP *request* bodies and both sets of headers ARE captured; the response body is not.** | D60 said bodies "are not captured" because the instrumentation does not record them. True, but the wrong reason to stop: `HTTPXClientInstrumentor` takes `request_hook`/`response_hook`, a real seam nobody had looked for. Measuring it split the question. The REQUEST body is already buffered when the hook fires, so reading it consumes nothing. The RESPONSE body is unreachable *on this span* — the instrumentation wraps the transport, so the span ends when `handle_async_request` returns and httpx reads the body afterwards in `Client.send`; attributes set on an ended span are dropped in silence. D60's conclusion was right by accident for half the problem and wrong for the other half. |
| D68 | 2026-08-15 | We will **not** buffer the response body to close that gap. | It is technically possible: read the stream in the hook and hand the caller a replacement. It would also turn every streaming download in the customer's process into a full in-memory read, to satisfy our telemetry. A monitoring tool that changes the memory profile of the thing it monitors has stopped being one. The console states the gap and its reason instead. |
| D69 | 2026-08-15 | There is **no `http_response_body` column** — migration 011 drops the one 009 added. | An always-empty column is worse than a missing one: it reads as "this call had no response body", a wrong answer where we otherwise give none. Also the first real test of the migration checksum guard, which refused the tidier fix of editing 009 in place and was right to — a drifting checksum means two installations silently disagree about their schema. So 009 stays as applied and 011 carries the correction. |
| D70 | 2026-08-15 | HTTP headers are captured by **allow-list, never deny-list**. | A deny-list captures every header nobody thought of, and the one nobody thought of is where the next bespoke `x-acme-session` credential lives. `authorization` and `cookie` are not read at all, rather than read and then scrubbed. The demo deliberately sends a bearer token on `submit_order` so this is verified against the live database, not only in a unit test. |
| D71 | 2026-08-15 | **D64 unlocked: `clientInfo` is promoted to span attributes** (`mcpobs.client.name` / `.version`) and to columns. | D64 found client identity inside `_meta`; that left it reachable only through payload capture, which is off by default. Client identity would then have been a side-effect of enabling something far more invasive. Two low-cardinality strings, set on success as well as failure — recording them only on failures would answer "which clients call which tools" with a breakdown of failures, which is subtly wrong and therefore worse than silence. Self-reported and unverified per the spec: display only, never an authorisation input. |
| D72 | 2026-08-15 | **DF-12 closed: `db.operation` and `db.collection` are derived from `db.statement`.** | The instrumentation emits neither, so "which table is slow" needed someone to read every statement by eye — both were derivable all along from data we already stored. Regex SQL parsing is defensible only because of what it is used for: two low-cardinality labels to group by, where anything unparseable yields empty — the status quo — and never a guess. A wrong table name would silently misattribute latency. |

| D73 | 2026-08-15 | **One rollup table, not the two DF-7 named.** `server_metrics_1m` is `tool_metrics_1m` with the tool column dropped. | Two materialized views would be two copies of the same arithmetic, free to drift, and the register's own framing invited that. With `mcp_tool_name` in the sort key, `GROUP BY service_name` answers the server question *exactly* -- `uniqExact` over a key column is not an estimate. A second table would have bought a second source of truth and nothing else. |
| D74 | 2026-08-15 | `failure_category` is part of the rollup's sort key. | Every summary view wants counts *and* a breakdown. With the category in the key the breakdown is a `GROUP BY`; without it, it needs a separate aggregate state per category. It multiplies rows by the category count, which is fixed at eight. |
| D75 | 2026-08-15 | **A materialized view cannot honour D24, so aggregates get a second maintainer: `scripts/recompute_rollups.py`.** | An MV sees an insert batch, not a version history, so a replay ADDS to its counters instead of superseding. This is not fixable inside the MV. Aggregates are therefore maintained by the MV in the normal case and rebuilt by the script after a replay -- the same class of operation as the replay itself. It uses `REPLACE PARTITION` from a staging table, so a repair never shows a hole to a reader mid-run. |
| D76 | 2026-08-15 | Assertion E1 is **split into drift and repair**. | `make verify` already replays a span (B11b). E1a asserts the drift is visible; E1b asserts the recompute fixes it. Asserting only the repair would hide that drift is possible; asserting only the drift would leave the repair untested. |
| D77 | 2026-08-15 | **`trace_summaries` had the same defect since Day 2, and B4 could not see it.** | It is a materialized view too, so it double-counted replayed spans from the start. B4 compared `sum(span_count)` against `count()` on `spans_raw` -- both populations included the duplicates, so the two errors cancelled and the assertion passed while agreeing with a double-count. Only visible once the recompute made one side correct. B4 now compares against the argMax-resolved span population, and the recompute covers both aggregates. |
| D78 | 2026-08-15 | **DF-3 closed: `trace_summaries` is partitioned by a date taken from the ROW, not from an aggregate.** | 004 recorded that "every candidate date lives in an aggregate column whose value changes as parts merge". True of `min(timestamp)`, and irrelevant: `toDate(timestamp)` of the span being inserted is deterministic and never changes. The blocker was assuming the trace's date had to be a property of the trace rather than of the row. |
| D79 | 2026-08-15 | A trace straddling midnight becomes two summary rows, and that is accepted. | The cost 004 named is real. Its frequency is not: a trace lasting T seconds straddles with probability T/86400, about one in eight million at 10ms per trace. Any reader that does `GROUP BY trace_id` merges the halves exactly -- and reading an AggregatingMergeTree already requires aggregating across unmerged parts, so a correct reader pays nothing. |
| D80 | 2026-08-15 | `trace_summaries` keeps **7-day retention matching `spans_raw`; the metric rollup gets 90 days**. | A rollup row is a statistic and stands alone. A trace summary is a LINK -- every row implies a drill-down into spans that must still exist. A summary outliving its spans would put rows in the console that 404 when clicked, which is worse than not showing them. |
| D81 | 2026-08-15 | **DF-4 closed as a product caveat: the clock tick is measured per service and the console refuses to present percentiles it cannot support.** | DF-4 sat on WATCH being reported by `make verify` every run -- which means it was told to *us* and never to the customer, while the console printed an unqualified number. The register said the decisive part itself: Linux is nanosecond-grade so our production is probably fine, **a customer on Windows is not**. That makes it a product caveat, not a test-rig footnote. |
| D82 | 2026-08-15 | The caveat has **two independent triggers**, and neither subsumes the other. | A p50 within 10x of the tick is quantisation however few zeros there are. A p50 comfortably above the tick still misleads when most calls floored to zero, because the survivors are a biased tail rather than a sample of the whole. |
| D83 | 2026-08-15 | The clock verdict is computed **server-side and shipped as a string**, not as a flag the browser interprets. | The previous banner hardcoded "~0.75ms" -- a value measured once on one laptop and frozen into the UI, wrong for every other host and silent when the clock was fine but calls still floored to zero. The tick is now measured where the spans are, and the reason travels with the number to every place it is read, including table cells. |

| D84 | 2026-08-15 | **DF-15 answered by measurement: the Collector cannot resolve an API key to trusted tenant attributes, so a thin auth gateway sits in front of it.** | `otel/opentelemetry-collector-contrib:0.115.1` ships `basicauth`, `bearertokenauth`, `oidcauth`, `asapauth`, `sigv4auth`, `oauth2client` and `headers_setter`. Every one answers "is this request allowed?"; none writes a resolved tenant onto the Resource. The authenticator interface puts data in the request context and nothing stock moves it from there. The choice was a custom Go extension or a shim; this is the shim. ADR-003's substance survives -- batching, retry, queueing, backpressure and Kafka production all remain the Collector's, which is what the ADR was actually protecting. |
| D85 | 2026-08-15 | The gateway **parses and re-serialises** every payload to overwrite `tenant.id`, rather than passing it through. | The point is that the customer's own value must not survive. Existing keys are dropped before the trusted ones are appended: appending alone would leave two `tenant.id` entries and make the winner depend on whichever consumer read last, which is a coin toss rather than a boundary. |
| D86 | 2026-08-15 | **The Collector's OTLP ports are no longer published, and its hard-coded tenant stamping is deleted.** | Both were required for the auth to mean anything. A published 4318 is an unauthenticated bypass sitting beside the front door; and the old `resource/tenant` processor would have OVERWRITTEN the authenticated tenant with `local`, collapsing every customer into one. A "fallback default" would do the same damage precisely when the gateway was bypassed, which is when you least want it -- so untenanted payloads stay untenanted and visible. |
| D87 | 2026-08-15 | Ingest and read are **separate scopes**. | They leak differently: an ingest key lives in a customer's server process and deployment config, a read key in a browser. One being compromised must not imply the other. Assertion F2 fires an ingest key at the read plane. |
| D88 | 2026-08-15 | API keys are stored as **plain SHA-256**, and that is deliberate rather than lazy. | bcrypt and argon2 exist to make brute force expensive against LOW-entropy inputs -- human passwords. This secret is 256 bits from `secrets.token_urlsafe`, so brute force is not the threat model, and a deliberately slow hash would add its cost to the authentication of every ingest request in the hot path. Hashing at all is what matters: a leaked dump must contain no usable keys. The reasoning does not transfer to a password column, and the schema says so where someone would otherwise copy it. |
| D89 | 2026-08-15 | The key-resolution cache stores the **secret hash alongside the principal**. | Caching only the principal would have let any secret through once a valid prefix was warm; re-reading Postgres to check would not have been a cache at all. Negative results are cached too, so a key-spraying attacker cannot turn authentication into a denial of service against the control plane. TTL is 30s, which IS the documented revocation delay and the Postgres-down survival window (Architecture.md §8). |
| D90 | 2026-08-15 | **Invite-only is a property of the schema, not a rule in the API.** | There is no signup table and no code path that creates a user except redeeming an invite; the redeeming UPDATE is conditional on `accepted_at IS NULL`, so two simultaneous redemptions cannot both win. An API-layer check is one forgotten branch away from an open front door. `scripts/admin.py bootstrap` is the only way to create an org and is not reachable over HTTP -- the moment an endpoint mints an org, invite-only is a policy rather than a property. Assertion F6 checks no user exists without a redeemed invite. |
| D91 | 2026-08-15 | Tenancy in the query API comes from the key and the `?tenant=` parameter is **removed, not deprecated**. | Leaving it as an override "for admins" is how a tenancy boundary becomes optional, and an optional boundary is not one. The repository was already written so endpoints never choose a tenant (Day 3), so this changed where the value comes from and nothing else -- which is the whole reason that shape was chosen then. |
| D92 | 2026-08-15 | The archive is a **Kafka consumer group**, not the Collector's `awss3` exporter. | The exporter would have been less code and would archive BEFORE Kafka -- so the archive would contain what we intended to send rather than what the pipeline actually consumed. Reading from the topic, with its own lag and its own replay position, is what makes it a faithful copy rather than a parallel opinion. |
| D93 | 2026-08-15 | The archive stores **raw OTLP protobuf, not parquet** -- deviating from Architecture.md §4. | ADR-007 settled it already: "One replay mechanism is worth paying for." Replay means feeding these bytes back through the same consumer. Parquet needs a second replay path that reads columns instead of messages, which is exactly the split ADR-007 rejected. The cost is real and stated: the archive is not directly queryable by Athena. Queryable long-term telemetry is ClickHouse's job, and a parquet projection can be derived from the archive later -- the reverse cannot. |
| D94 | 2026-08-15 | Archive objects are keyed **tenant first**, with the Kafka offset range in the filename. | Tenant first makes "delete everything belonging to this customer" a prefix delete and a per-tenant lifecycle rule a prefix rule; date first would make both a full scan, and GDPR erasure is not something to discover you cannot do cheaply. Offsets rather than a timestamp or uuid make a retry after a crash between put and commit overwrite the identical object instead of creating a second copy. |
| D95 | 2026-08-15 | Payloads are **framed with explicit lengths** before compression. | Protobuf is not self-delimiting: two concatenated `ExportTraceServiceRequest`s parse as one merged message, silently, with repeated fields joined. The archive would still look valid and would no longer contain the messages it claims to. |
| D96 | 2026-08-15 | The archiver is MCP-unaware but **tenant-aware**, and must be. | Architecture.md §4 says it does nothing MCP-aware, and it does not -- it never reads a span, a method or a payload. It does read `tenant.id` off the Resource, because one message can carry SEVERAL tenants (the Collector's batch processor merges concurrent requests) and keeping one customer's bytes out of another's object is the entire reason the key layout exists. |

| D97 | 2026-08-15 | **Downstream instrumentation is documented two ways, and the OTel agent is named first.** | `opentelemetry-instrument python -m your_server` is the better answer whenever it is available: it is OTel-native, we maintain nothing, and it picks up a new instrumentation package the day the customer installs it. Recommending our own helper first would be recommending our code over a standard that already works. |
| D98 | 2026-08-15 | **`instrument_downstream()` exists anyway, because a large share of MCP servers do not own their command line.** | They are spawned by the CLIENT over stdio -- Claude Desktop, an IDE, another agent -- so there is no command to prepend `opentelemetry-instrument` to. That case is specific enough to MCP that an in-process equivalent earns its place rather than duplicating the agent for the sake of it. |
| D99 | 2026-08-15 | It **discovers** instrumentors through the `opentelemetry_instrumentor` entry-point group rather than naming them. | That is the mechanism the agent itself uses, so `pip install opentelemetry-instrumentation-redis` is the entire integration: no mcpobs release, and no hardcoded list to forget to update. |
| D100 | 2026-08-15 | It returns a **report** and never raises. | A call that patches an unknown set of libraries and says nothing is not something anyone should put in a production server, so the customer gets `{name: outcome}` back. Each instrumentor is attempted independently: one package with a version conflict is reported and skipped, never allowed to stop a server booting. An observability library that prevents a server from starting has done more damage than the telemetry was worth. |
| D101 | 2026-08-15 | It stays **opt-in**; `instrument(server)` does not call it. | Patching a customer's database driver as a side effect of "observe my MCP server" is not something to do quietly. Same reasoning that keeps `instrument_httpx()` separate (D60). |
| D102 | 2026-08-15 | **The httpx2 claim was wrong: contrib ships `HTTPX2ClientInstrumentor` and it works.** | `demo_server/server.py` had carried a comment since Day 1 saying the SDK's httpx2 was not instrumentable, and the demo used plain httpx to work around it. Measured: the entry point exists, loads, and emits spans against a real request. So the MCP SDK's OWN transport calls are observable, which we had written off. Another instance of a limitation recorded from the absence of a feature rather than the absence of a seam (cf. D67). |
| D103 | 2026-08-15 | Order between `instrument_downstream()` and `instrument_httpx()` is **free**, and that is asserted with real requests. | OTel's `BaseInstrumentor` is a singleton whose `instrument()` no-ops while active, so body-capture hooks survive either order. Checked by making an actual HTTP request over a real socket in both directions -- inspecting `is_instrumented_by_opentelemetry` would only have confirmed that our own guard ran, which is not the question. A customer will get the order wrong half the time and nothing should depend on it. |
| D104 | 2026-08-15 | The demo bootstrap now calls `instrument_downstream()` instead of naming instrumentors by hand. | A demo that integrates differently from the documentation is how the documentation goes stale without anyone noticing. |
| D105 | 2026-08-15 | Test teardown restores the **raw** `trace._TRACER_PROVIDER`, never `get_tracer_provider()`. | With none set, that call returns the ProxyTracerProvider, and restoring the proxy into the global makes it delegate to itself -- a RecursionError 900 frames deep inside the MCP SDK, presenting as four failing classifier assertions. The bug had been latent in `test_sdk_contract.py` since Day 2 and only sprang once a second test set a provider. `set_tracer_provider` is also guarded by a `Once`, so resetting the provider without resetting the guard silently sends spans to the previous test's exporter. |
